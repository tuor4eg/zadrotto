# Geekoteka

«Гикотека» — Next.js-приложение для картотеки игр, фильмов, сериалов, книг, комиксов, аниме и других культурных записей.

Сейчас проект включает публичный архив, кабинет автора, админку, оценки и рецензии, серии, обложки, импорт метаданных и вспомогательные AI-сценарии. Подробнее о продуктовых границах — в [`PROJECT_CONTEXT.md`](./PROJECT_CONTEXT.md).

## Стек

- Next.js 16, React 19, TypeScript;
- PostgreSQL и Drizzle ORM;
- Tailwind CSS;
- S3-compatible storage для обложек;
- Redis для rate limit;
- `node:test` через `tsx`.

## Локальный запуск

Требуются Node.js 20+, PostgreSQL и Redis. Для работы с обложками нужен S3-compatible storage; локально можно использовать MinIO.

1. Подготовь окружение:

```bash
cp .env.example .env
npm install
```

2. Укажи в `.env` как минимум:

```env
DATABASE_URL=postgres://user:password@localhost:5432/zadrotto
SITE_URL=http://localhost:3000
ADMIN_LOGIN=admin
ADMIN_PASSWORD=change-me
ADMIN_SESSION_SECRET=change-this-to-a-long-random-secret
AUTHOR_SESSION_SECRET=change-this-to-another-long-random-secret
AI_PROVIDER_CREDENTIALS_KEY=change-this-to-a-separate-long-random-ai-provider-key
REDIS_URL=redis://127.0.0.1:6379
```

Секреты сессий и ключи шифрования должны быть длинными случайными значениями. `ADMIN_PASSWORD` используется только seed-скриптом; в базе хранится hash.

3. Накати миграции и создай первого администратора:

```bash
npm run db:migrate
npm run db:seed:admin
```

4. Запусти приложение:

```bash
npm run dev
```

Основные адреса:

- публичный архив — <http://localhost:3000>;
- админка — <http://localhost:3000/admin>;
- вход автора — <http://localhost:3000/author/login>.

Администратор входит по логину и паролю. Автор использует выданный администратором access token либо регистрацию, если она включена. Сессии хранятся в `httpOnly` cookie; исходные access token в базе не сохраняются.

## Обложки и MinIO

Поднять Redis и MinIO из production compose-файла для локальной разработки можно так:

```bash
docker compose --profile local up -d redis minio
```

Консоль MinIO будет доступна на <http://localhost:9001>. Создай bucket из `S3_BUCKET` и разреши публичное чтение объектов. Настройки подключения уже перечислены в `.env.example`.

Приложение умеет загружать обложки, искать варианты через настроенных провайдеров и создавать уменьшенные версии. `media_items.cover_url` поддерживает object key внутри bucket и готовый `http(s)` URL.

Для существующих обложек можно запустить:

```bash
npm run covers:backfill-thumbs
```

## Внешние и AI-провайдеры

Источники названий, метаданных и обложек настраиваются в разделе инструментов администратора.

AI настраивается в `/admin/tools/ai`:

1. В «Провайдерах» сохрани credentials, обнови список моделей и выбери модель по умолчанию.
2. Проверь модель тестовым prompt.
3. В «Сценариях» настрой и включи нужную системную операцию.

Сейчас зарегистрированы OpenRouter и прямой DeepSeek API, а также сценарий «Предложить серии». Сценарий наследует модель и параметры провайдера, если они явно не переопределены. Credentials шифруются ключом `AI_PROVIDER_CREDENTIALS_KEY` и не передаются в браузер или логи. AI-результат всегда проверяется сервером и не считается источником истины.

## Регистрация авторов и email

Регистрация управляется переменной `AUTHOR_REGISTRATION_ENABLED` и настройками в `/admin/settings/authors`. Для локальной разработки можно задать:

```env
AUTHOR_REGISTRATION_SKIP_EMAIL_VERIFICATION=true
TURNSTILE_SITE_KEY=1x00000000000000000000AA
TURNSTILE_SECRET_KEY=1x0000000000000000000000000000000AA
TURNSTILE_REGISTRATION_BYPASS=false
```

В production пропуск проверки email игнорируется, а для Turnstile нужно указать реальные ключи виджета. Официальные тестовые ключи выше предназначены только для development и тестов. При длительной недоступности Cloudflare оператор может временно включить server-side флаг `TURNSTILE_REGISTRATION_BYPASS=true`: он отключает Turnstile только для регистрации, не затрагивая rate limits, honeypot и проверку времени заполнения. Состояние обхода показывается в `/admin/tools/services` и отмечается в журнале успешной регистрации. Email credentials и очередь настраиваются в `/admin/tools/email`; для них нужны `EMAIL_OUTBOX_ENCRYPTION_KEY` и `EMAIL_PROVIDER_CREDENTIALS_KEY`. Доставку писем и очистку auth-данных выполняет универсальный jobs worker.

## Универсальные фоновые задачи

Периодические определения хранятся в `jobs`, а каждый запуск — в `job_runs`. Scheduler читает только cron-расписания (пять частей, UTC) и создаёт запуски; worker получает только `job_runs` и выбирает обработчик по типу. Ручные и событийные операции используют тот же `enqueueJobRun` из `src/lib/jobs/queue.ts`.

Для запуска процессов вне Next.js доступны:

```bash
npm run jobs:scheduler
npm run jobs:worker
```

Миграция `0097_anime_shikimori_markup_refresh` однократно возвращает в очередь
обработанные anime из AniList с разметкой Shikimori в описании. После обновления worker
существующее задание само получит и очистит описания; ручная команда для этого деплоя не нужна.
Текст описаний миграция не меняет, русские описания без разметки не затрагивает.

Для дополнительных ручных повторных проходов доступны команды:

```bash
npm run anime:requeue-shikimori -- --dry-run
npm run anime:requeue-shikimori
```

Команда сбрасывает только маркер попытки у записей с пустым, явно английским описанием
или ссылочной разметкой Shikimori. Русские описания без этой разметки сохраняются.
Описания обновляет существующее задание `media.anime-shikimori-backfill`;
scheduler, worker и расписание задания должны быть включены.

В Compose используются образы `ghcr.io/tuor4eg/zadrotto-jobs:latest`; worker можно масштабировать без изменения логики очереди:

```bash
docker compose up -d jobs-scheduler jobs-worker
docker compose up -d --scale jobs-worker=2 jobs-worker
```

Миграция создаёт задания `auth.email-outbox-delivery` и `auth.cleanup` выключенными. После первого развёртывания их нужно включить в `/admin/tools/jobs`; расписание и история запусков управляются там же.

## Production compose

`docker-compose.yml` использует готовые образы приложения, migrator и Node runner для фоновых задач:

```bash
docker compose --profile migrate run --rm migrate
docker compose --profile seed run --rm seed-admin
docker compose up -d app redis jobs-scheduler jobs-worker
```

Перед запуском заполни production `.env` и установи `SECURE_COOKIES=true`.

Миграция `0103_unified_genres` создаёт справочник жанров, provider mappings и заполняет
нормализованные связи из сохранённых metadata. Отдельные команды seed/backfill не нужны.
Перед её применением сделай резервную копию и останови `app`, `jobs-scheduler`, `jobs-worker`;
после успешного завершения запусти новые образы. Неизвестные значения, некорректные форматы
и отсутствующие provider выводятся как `WARNING` в журнал migrator, итог — как `NOTICE`.
Raw metadata остаются неизменными. Поддерживаются массивы строк и целое строковое название;
исторические разделители не предполагаются. Перед production rollout сверяй предупреждения
с исходным экспортом. Исправления существующих mappings выполняются следующими SQL-миграциями.

Миграция `0104_genre_requests` создаёт заявки на неизвестные жанры из текущих metadata
и постоянные исключения. В админке «Заявки → Жанры» можно создать внутренний жанр,
связать значение с существующими жанрами или исключить его. Решение автоматически
применяется к сохранённым записям существующим jobs-worker без обращения к провайдерам.
При ошибке повтор доступен из заявки; исходные metadata и ручные назначения сохраняются.
«Записи → Жанры» остаётся справочником названий. Для выпуска достаточно стандартной
миграции и обновления приложения вместе с jobs-worker; дополнительных команд не требуется.

## Создатели

Миграция `0117_creators` добавляет универсальных создателей, типы, роли и связи с записями
и сериями. Коды справочников задаются при создании и защищены от изменения в БД;
начальные значения — `person` и `writer`. Справочник и апрув доступны в `/admin/creators`,
общий публичный каталог — в `/creators` («Создатели»).

Для выпуска сначала примени миграцию, затем обнови приложение и jobs-worker.
В `/admin/tools/jobs` запусти разовую задачу `media.creators-backfill` с параметрами `{}`.
Она использует сохранённые metadata книг без запросов к провайдерам, объединяет точные
нормализованные имена людей и сохраняет существующие решения апрува и ручные связи.
Повторный запуск безопасен. Итоговые счётчики и ошибки отдельных записей доступны в журнале
действий (`media.creators-backfill.completed`); неоднозначные совпадения остаются на апрув.

### Создатели настолок BGG

BGG использует общую сущность Creator: роли `designer` («Дизайнер») и `artist` («Художник»)
принадлежат связи с записью. Один Creator может иметь обе роли. Тип `collective` («Коллектив»)
доступен наряду с `person`; существующие типы и Creator автоматически не меняются.

Миграция `0124_bgg_creators` расширяет общие provider bindings, заявки и происхождение связей.
BGG ID участника определяет личность независимо от роли и типа записи. Имя сохраняется для
отображения и диагностики. Только единственное точное совпадение по нормализованному имени
или оригинальному имени без другого BGG ID допускает автоматическое сопоставление.
Неизвестные, неоднозначные и конфликтующие участники попадают в `/admin/creator-requests`:
можно выбрать существующего Creator, создать нового с явным типом «Человек / Коллектив»
или игнорировать ID. Решение действует на все роли и записи этого BGG ID.
Возврат привязки или исключения на апрув доступен в существующей админке.

Полный валидный ответ BGG заменяет только BGG-источники связей соответствующей настолки.
Снятие роли или участника не удаляет Creator и сохраняет ручные связи и другие источники.
Старые metadata без ID и ошибки провайдера не считаются пустым составом. Публичный каталог
«Создатели» и фильтр архива учитывают все роли и типы; запись считается один раз даже при
нескольких ролях. В настолках подтверждённые Creator показываются группами дизайнеров и
художников. После перехода на структурированные ID сырые имена не возвращают исключённых
или ожидающих апрува участников.

Для заполненного прода после штатной миграции и обновления Docker-контейнеров приложения и
worker запусти в `/admin/tools/jobs` разовую задачу `media.bgg-creators-backfill`:
сначала с `{"dryRun":true}`, затем с `{}`. Дополнительных CLI-команд и npm-скриптов нет.
В обычном проходе неизвестный участник сначала получает заявку. Затем бэкфилл автоматически
принимает её через существующий механизм апрува: при отсутствии совпадений создаёт Creator
типа «Человек», при единственном безопасном совпадении связывает с существующим. Обычная
задача применения решения добавляет роли и связи в фоне. Неоднозначные случаи, конфликты,
исключения и вручную возвращённые заявки не подтверждаются автоматически.
Задача получает актуальные ID по уже сохранённому BGG ID записи через существующий BGG
pipeline: нужны настроенные Application Token, Redis и разрешённый провайдер.
Бэкфилл обновляет только технические ссылки участников и их связи; названия, описания,
обложки и редактируемые metadata не заменяются.

Параметры: `mediaItemId` для одной записи, `afterId` для возобновления, `limit` — размер
пакета (по умолчанию 25, максимум 100), `dryRun` — проверка API без изменения записей,
связей и заявок. Продолжения автоматически ставятся в очередь до конца выборки.
Повтор безопасен: bindings и решения используются по ID; обычный sync не подтверждает ожидающие заявки автоматически; разовый бэкфилл использует
описанный выше путь автоматического апрува. Результаты каждой записи и курсор доступны
в журнале `media.bgg-creators-backfill.progress`, итоги пакета — в
`media.bgg-creators-backfill.completed`. Временные ошибки повторяются ограниченно;
после устранения ошибки отдельную запись можно обработать через `mediaItemId`.
Бэкфилл не выполняется при сборке образа, SQL-миграции или старте приложения.

### Разработчики и издатели игр IGDB/RAWG

Миграция `0125_game_company_creators` добавляет тип Creator «Организация» и роли
«Разработчик» / «Издатель». Внешние идентичности — `igdb/company:<id>`,
`rawg/developer:<id>` и `rawg/publisher:<id>`; несколько идентичностей можно вручную
связать с одной организацией в общей системе заявок. Автоапрув использует единственное
точное нормализованное название организации: существующая организация получает binding,
при отсутствии совпадений создаётся новая. Неоднозначные названия, другой ID в том же
пространстве провайдера и вручную переоткрытые заявки остаются на проверке.

После обычного применения миграций и запуска worker открой `/admin/tools/jobs/schedules`
и выбери «Разовый запуск» → «Разработчики и издатели игр: импорт с автоапрувом»
(`media.game-companies-backfill`) с параметрами `{}`. Он охватывает
все статусы игровых записей с сохранёнными источниками IGDB/RAWG. При деплое ничего
автоматически не запускается. Требуются настроенные credentials, Redis и S3/MinIO.

Составы игр, профили компаний, файлы логотипов и этапы обработки сохраняются постоянно.
Перезапуск worker и ожидание бюджета не требуют повторного получения успешных данных.
Лимиты общие с обычными запросами провайдеров; backfill сохраняет дневной резерв 100
запросов и автоматически продолжает работу после восстановления бюджета. Временные
ошибки повторяются ограниченно; для оставшихся ошибок после исправления причины
повтори обычный разовый запуск. Прогресс и ошибки записываются в журнал действий
`media.game-companies-backfill.progress` / `media.game-companies-backfill.completed`
с привязкой к запуску задачи; состояние запуска видно в общем журнале jobs.

Неизвестные компании поступают в `/admin/creator-requests` и автоматически проходят
обычное решение заявки при однозначном совпадении либо создании организации.
Решение применяется ко всем
сохранённым составам соответствующего провайдера без новых запросов API. Ручные связи
и сведения другого провайдера сохраняются. Неактивные версии bindings сохраняют
происхождение до фонового пересчёта; действующая внешняя идентичность уникальна.

Логотип IGDB сохраняется до модерации, назначается из локальной копии и не заменяет
ручную аватарку. RAWG `image_background` не используется как логотип. На публичной
странице подтверждённые организации кликабельны, неизвестные остаются текстом.

### Аватарки Creator и FantLab ID

Миграция `0123_creator_avatars` добавляет локальные изображения Creator и подтверждённые
FantLab bindings по ID автора. Именные соответствия остаются диагностическими вариантами;
изображение и его происхождение хранятся у Creator. Приоритет: ручная аватарка → FantLab →
отсутствие изображения (публичный fallback с инициалами добавляется отдельно).
Ручная загрузка с кадрированием, удаление изображения, проверка/назначение FantLab ID и
повторный sync доступны в редакторе Creator. Автоматический sync никогда не заменяет ручную
аватарку. Отсутствие фото или ошибка FantLab сохраняют предыдущую локальную копию.

Выпуск выполняется обычными Docker-образами приложения, migrator и jobs-worker.
Дополнительных CLI-команд и npm-скриптов нет. После штатного применения миграции и обновления
контейнеров открой `/admin/tools/jobs` и выполни разовые задачи в следующем порядке:

1. `media.creator-fantlab-bindings` с параметрами `{"dryRun":true}` — предварительный отчёт
   по миграции существующих именных соответствий. Только единственное точное совпадение
   допускается к автоматическому подтверждению ID; неоднозначные и конфликтующие случаи
   остаются для ручного разрешения в редакторе Creator.
2. Та же задача с `{}` — сохранить однозначные ID. Она не создаёт Creator, роли или связи
   с записями и не переопределяет уже подтверждённые ID поиском по имени.
3. `media.creator-fantlab-avatars` с `{"dryRun":true}` — проверить доступность изображений
   без сохранения файлов и изменения Creator.
4. Та же задача с `{}` — загрузить аватарки в собственное S3/MinIO-хранилище.

Задачи обходят Creator пакетами и сами ставят продолжение в очередь до конца выборки.
`limit` (по умолчанию 50, максимум 200) задаёт размер пакета, а не общий предел обхода;
`creatorId` ограничивает обработку одним Creator; `afterId` позволяет возобновить проход
после указанного ID. И `dryRun`, и обычный проход безопасно запускать повторно. Для обоих
типов задач нужны доступные Redis (общая очередь запросов FantLab), PostgreSQL и worker;
для сохранения изображений — настроенное S3/MinIO.

Результат каждого Creator и курсор сохраняются в журнале действий
`creator.fantlab-sync.progress`; итоги пакета — в `creator.fantlab-sync.completed` с ID
запуска. В отчёте различаются подтверждённые и неоднозначные ID, конфликты, отсутствие фото,
ручные аватарки, обновления, неизменившиеся данные и ошибки. После прерывания можно повторить
проход с `{}` либо продолжить с последнего сохранённого `afterId`. Перед запуском следующего
этапа дождись завершения всех продолжений текущего. Ошибки отдельных Creator не останавливают
обход: устрани причину и повтори запуск для нужного `creatorId`.

Новые данные авторов из FantLab связываются с существующими Creator только по подтверждённому
ID; имена не используются для выбора Creator. Неизвестные ID и конфликты вариантов имени
попадают в журнал, старые metadata без ID сохраняют существующие связи без перепривязки.
Бэкфилл не выполняется при сборке Docker-образа, внутри SQL-миграции или при старте приложения.

Решения и разрыв provider mapping применяются задачей `media.creator-request-apply`.
До завершения задачи архив может показывать прежние связи; после ошибки доступен повтор.
После возврата последнего mapping создатель удаляется, если после пересчёта у него не осталось
связей с записями, сериями или другими provider mappings. Ручные назначения сохраняются.
Связанные серии показываются ссылками и не расширяют выборку записей создателя.

## Ручной дамп базы

В `/admin/exports` кнопка «Создать дамп базы» ставит задачу в существующую очередь.
После завершения там появляется файл `.sql.gz`, доступный только создавшему экспорт
администратору. Для обновления статуса нажми «Обновить». Бэкапы хостера работают независимо.

Перед выпуском примени миграцию `0113_admin_database_dump` и обнови образы `app` и
`jobs-worker`. Образ jobs содержит PostgreSQL client 18: сервер не должен быть новее клиента.
При обновлении PostgreSQL обнови и пакет клиента в Dockerfile. Для локального worker установи
`pg_dump` той же основной версии, что и сервер, либо более новой поддерживающей этот сервер.

Worker подключается по `DATABASE_URL`; нужны права читать все таблицы, последовательности
и large objects всех пользовательских схем. При RLS требуется право выгрузить все строки;
обычный доступ приложения к отдельным строкам недостаточен. Не выдавай приложению superuser
ради дампа. Для экспорта нужен прямой адрес PostgreSQL либо пулер в режиме session pooling.
Параметры SSL сохраняются; URI с `sslpassword` не поддерживается.

Новые дампы сохраняются в закрытых локальных файлах, без S3. В Docker приложение и
worker используют общий named volume `admin_exports`: приложение читает его, worker
записывает и удаляет файлы. Оба процесса работают с UID/GID 1001; каталог имеет права
0700, файлы — 0600. Volume не публикуется веб-сервером; скачивание идёт через проверку
администратора и владельца экспорта. После обновления образов примените новый compose
для приложения и worker. Не удаляйте volume, пока нужны готовые дампы.

При локальном запуске каталог задаётся `ADMIN_EXPORTS_DIR` (по умолчанию
`.data/admin-exports`). Приложение и worker должны видеть один и тот же каталог.
Обеспечьте место под полный сжатый дамп. Незавершённый файл имеет суффикс `.partial`;
повтор задачи и очистка истёкших экспортов удаляют его. Готовый файл публикуется
атомарным переименованием. Старые S3-экспорты по-прежнему читаются и очищаются;
`ADMIN_EXPORTS_S3_BUCKET` нужен только для таких ранее созданных дампов.

Одновременно выполняется один дамп базы, тайм-аут задачи — 1 час, до трёх попыток.
Срок хранения файла считается с момента готовности, берётся из настройки экспортов
(по умолчанию 7 дней); задание `admin.export-cleanup` должно быть включено.

Дамп содержит структуру и данные всей одной базы: включая пользовательские схемы,
индексы, ограничения, функции, процедуры, триггеры, представления, бинарные данные,
large objects, определения последовательностей и их значения. Владельцы и grants
не копируются: владельцем восстановленных объектов становится пользователь восстановления.
Роли, tablespaces и настройки внешних планировщиков сохраняются отдельно.

Для восстановления подготовь совместимый PostgreSQL и установленные в исходной базе
расширения (в проекте используется `pg_trgm`). Если политики ссылаются на роли, создай их
заранее. Настрой подключение `psql`/`createdb` через стандартные `PGHOST`, `PGPORT`, `PGUSER`
и пароль через `.pgpass`; используй роль, которой разрешено создавать необходимые объекты.
На новом сервере создай пустую базу и загрузи SQL, не применяя миграции перед восстановлением:

```bash
createdb --template=template0 geekoteka_restored
gzip -t geekoteka-db.sql.gz
gunzip -c geekoteka-db.sql.gz | psql -X --set=ON_ERROR_STOP=1 --dbname=geekoteka_restored
```

После восстановления проверь количество строк, функции/триггеры и создание новой записи
с корректным следующим ID. При пробном восстановлении используй отдельные S3/Redis
и не запускай worker/scheduler до проверки: дамп включает очереди задач и писем.

SQL-дамп не содержит файлы обложек/S3 и окружение. Для расшифровки сохранённых секретов
сохрани исходные значения `COVER_PROVIDER_CREDENTIALS_KEY`, `AI_PROVIDER_CREDENTIALS_KEY`,
`EMAIL_PROVIDER_CREDENTIALS_KEY`, `NOTIFICATION_TRANSPORT_CREDENTIALS_KEY`,
`EMAIL_OUTBOX_ENCRYPTION_KEY` отдельно в менеджере паролей. После ротации ключей сохрани
и значения, соответствующие более ранним дампам. Административный session secret можно
заменить, существующие административные сессии при этом завершатся.

Интеграционный тест создаёт и удаляет две отдельные тестовые базы, применяет миграции,
формирует дамп, восстанавливает его через `psql`, проверяет данные и очистку локальных файлов.
Запускай только с адресом выделенного тестового PostgreSQL и установленными `pg_dump`/`psql`:

```bash
NODE_PATH=./node_modules/next/dist/compiled NODE_OPTIONS=--conditions=react-server \
DATABASE_DUMP_TEST_DATABASE_URL=postgresql://localhost/postgres \
./node_modules/.bin/tsx --test tests/database-dump-db.test.ts
```

### Логотипы игровых платформ

Миграция `0126_platform_logos` добавляет только схему и не создаёт платформы, маппинги или игровые связи. После её применения задача **«Синхронизация логотипов платформ»** (`media.platform-logos-sync`) вручную запускается в админке jobs с `{}`. Параметр `{"force":true}` обновляет профили провайдеров, `{"platformId":123,"force":true}` обрабатывает одну существующую платформу. Автозапуска при деплое нет.

Задача использует сохранённые внешние ID. Для отсутствующих ID допускается только единственное точное нормализованное совпадение названия существующей привязки у соответствующего провайдера; остальные случаи пропускаются с записью в журнал без заявки. Внешний справочник не создаёт новые канонические платформы. Обработка идёт по каждой платформе до заявки/результата; ошибки загрузки повторяются после остальных платформ.

Для одной платформы создаётся одна актуальная заявка с картинками: нажать нужную и выбрать **«Использовать выбранное»** либо **«Без логотипа»**. Одинаковые файлы объединяются по хешу. Единственное изображение IGDB для точной платформы подтверждается автоматически; объединённые платформы, несколько разных изображений и RAWG требуют выбора. Если изображений нет, заявки нет. Решение применяется штатной `media.platform-request-apply` из локального кеша.

Ручная загрузка имеет приоритет; её удаление возвращает подтверждённый импортированный логотип, доступный и для объединённых платформ. Изображения сохраняются целиком, без кадрирования. Задачи продолжаются после лимитов через штатный defer. Прогресс и результаты доступны в журнале; активные запуски показываются перед завершёнными.

## Исходные снимки книжных провайдеров

Миграция `0127_provider_snapshots` добавляет универсальные `provider_snapshots` и
`provider_snapshot_links`. Полные ответы FantLab, Google Books и Open Library сохраняются
отдельно от рабочих данных, в том числе для предварительного импорта. Старая
`media_item_provider_snapshots` остаётся временным доказательством для автомодерации.
Миграция не запускает бэкфилл и не удаляет прежние `facts`.

Управление: `/admin/tools/providers/snapshots` или «Данные источника» в редакторе книги.
Доступны получение без применения, повторная обработка без сети, оба действия и проверка.
Прогресс массовой обработки показан на этой же вкладке: успешные записи, ошибки и общий
счётчик пройденных записей обновляются автоматически. Журнал открывается отдельно.
Для отдельной книги результат остаётся на странице её источника: статус задачи обновляется
автоматически, отдельно показаны дата сохранения ответа и сравнение с рабочими данными.
Задача `provider.snapshots` разовая, без расписания; параметры и checkpoint видны в журнале.
Размер партии задаётся перед запуском (1–100 книг, по умолчанию 25), как и пауза в часах
(0 — 1 секунда; 0,5 — полчаса; 24 — сутки). После последней партии паузы нет.
Известный источник, общий лимит каждого HTTP-запроса и резерв 100 запросов
для фонового получения. Возобновление использует сохранённые ответы текущего запуска.
При ошибках обработки список ID сохраняется в checkpoint; после исправления создайте задачу
для этих ID (`mediaItemIds`) или нужного диапазона. Не используйте старую задачу
автоодобрения создателей для миграции.

FantLab, Google Books и Open Library постоянно используют нормализованные связи авторов и
издателей. В хранимом `facts` книги остаётся `originalLanguage` либо `{}`. Импорт и offline replay
требуют проверенного комплекта raw-снимков; отдельного включения нового режима больше нет.
Книжный псевдоним, ручные назначения и решения модерации сохраняются.

Миграция `0132_book_language_facts` перенесла язык обратно в JSON и удалила отдельную колонку.
Миграция `0133_book_snapshot_contract` удаляет временный флаг `normalized_book_metadata`.
Если в обновляемой БД ещё есть книги поддерживаемого провайдера с незавершённым переходом,
миграция остановится без изменений: сначала завершите переход на предыдущей версии приложения.
Для новой пустой БД дополнительного включения не требуется. Применяйте миграцию вместе с
обновлением приложения и workers; старый код обращается к удаляемому флагу.

Опция «Только без сохранённого снимка» доступна для получения и получения с применением
у книг, фильмов и создателей. Она проверяет основной raw текущего источника по ресурсу,
методу и параметрам запроса. Снимок учитывается даже без links и независимо от `facts`:
это фильтр отсутствующих исходных ответов, а не неприменённых данных. Для Open Library
наличие снимков авторов не заменяет основной снимок произведения; отсутствие зависимостей
не делает уже сохранённый основной снимок отсутствующим. Offline-обработка и проверка
используют сохранённые ответы и не предлагают этот фильтр. При сбое начатый ID остаётся
в checkpoint: возобновление завершает его применение без повторного получения raw.

Снимки — только актуальные ответы, не аудит истории. При удалении/слиянии сущности
обязательно использовать общий транзакционный сервис связей: полиморфная ссылка не имеет
FK на произвольную доменную таблицу. Raw JSON не передаётся в токенах и журналах и доступен
только отдельной административной странице. Размер одного ответа ограничен 2 МиБ.

### Исходные снимки фильмов TMDB

В `/admin/tools/providers/snapshots` выберите TMDB: обрабатываются только фильмы с уже выбранным TMDB ID, без поиска новых источников. Для первой проверки задайте небольшой диапазон ID. Данные одной записи доступны по ссылке «Данные источника» в редакторе фильма.

1. «Получить данные» (`refresh`) сохраняет полный movie details с `credits`, не меняя запись.
2. Сравните текущие характеристики с проекцией; `verify` отмечает расхождения, не исправляя их. Отсутствие старого ключа допустимо для ранее незаполненной записи; отличающееся существующее значение требует проверки.
3. «Применить сохранённые данные» (`process`) работает без сети. «Получить и сразу применить» (`refresh-process`) выполняет оба шага. Основные редакционные поля, обложки и участники не изменяются; жанры используют прежние правила и решения модерации.
4. После проверки партии запускайте ручной бэкфилл с нужными размером партии и паузой. Продолжение хранится в checkpoint задания, верхняя граница ID фиксируется при старте; временные сбои повторяются штатными jobs. Не создавайте новый массовый запуск вместо ожидающего продолжения. Для окончательно неуспешных записей используйте отдельный повторный запуск по их диапазону или карточке.

Миграция `0134_tmdb_film_genre_facts` удаляет только `genres` и `genreReferences` из `facts` фильмов TMDB. Она проверяет связанные primary-снимки текущих источников и при пропуске отменяет очистку целиком; HTTP-запросов нет. Внутренние жанры остаются в `media_item_genres`, ручные связи и решения модерации не меняются. При выкладке остановите старые workers, обновите web-приложение, выполните `npm run db:migrate`, затем запустите обновлённые workers. Дальнейшее применение снимков не возвращает удалённые поля.

Старые данные не очищаются при ошибке получения или проверки снимка. Дополнительные legacy-ключи `facts` сохраняются на переходном этапе. Удалять их следует отдельным целевым изменением после проверки SQL/TS-потребителей, универсального отображения, фактических ключей и успешной миграции; нужные ненормализованные характеристики остаются. Полный raw сохраняется независимо от очистки `facts`. Новых сущностей из `credits` этот этап не создаёт.
