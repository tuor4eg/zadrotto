# Объединение аккаунтов

Объединение — общая доменная операция, не часть адаптера Яндекса. Адаптер подтверждает
identity; конфликт `link` создаёт SQL-разрешение на 10 минут, связанное с текущей сессией,
двумя авторами, identity и revision конфигурации. Профили не объединяются по email.
`/author/profile/merge` показывает обе стороны и предлагает выбрать основной профиль целиком.

## Подтверждение и конкурентные изменения

`createAccountMergeGrant`, `getAccountMergePreview`, `confirmAccountMerge` находятся в
`src/db/operations/account-merge.ts`. Подтверждение получает только grant ID, основной ID из
разрешённой пары и SHA-256 версию предпросмотра. Данные, статус аккаунтов, действующая сессия,
владелец identity, revision и срок повторно проверяются внутри транзакции.
Смена любой затрагиваемой строки, кроме `sessions.last_seen_at`, требует нового предпросмотра.
Отмена не меняет данные; неиспользованное разрешение истекает.

Для раннего MVP выбран короткий общий барьер `SHARE ROW EXCLUSIVE` на явно перечисленных
таблицах переноса. Он временно задерживает записи **всех пользователей** в этих таблицах,
но позволяет чтение. Это сознательное ограничение первой версии; длительность растёт с
объёмом двух аккаунтов. `lock_timeout=5s`; deadlock/serialization повторяет всю транзакцию
до трёх попыток. Частичные переносы не коммитятся. Не запускать объединение фоновыми батчами
с отдельными commit без нового проектирования блокировок и пользовательской семантики.

Порядок: shared reputation lock → табличный барьер → author advisory locks по ID → строки
авторов. Триггеры mutable author FK блокируют OLD/NEW авторов и отвергают закрытый профиль;
дополнительно защищены polymorphic notifications и дочерние строки рецензий. Они действуют
для приложения, workers и прямого SQL. Узкое исключение DELETE разрешает retention cleanup
уже отозванных sessions/access tokens и использованных challenges закрытого автора. Сами tombstone-авторы неизменяемы. Исторические
`domain_events` и `admin_activity_logs`, grants и закрытый архив исключены из write guard.

## Политика данных

`ACCOUNT_MERGE_POLICIES` — явный серверный перечень таблиц. Тест сверяет его с FK на `authors`;
notifications учтены отдельно, потому что recipient полиморфный. Имена таблиц из HTTP не принимаются.

- Основной автор сохраняет ID, code, имя, аватар, источники полей, права и настройки.
- Ratings сопоставляются по записи/части (NULL — общая оценка), reviews — по записи/части.
  Желаемое конфликтует со всеми оценками той же записи; состояние основного побеждает.
- Недостающее переносится с прежними ID, датами и статусами модерации. Конфликтующая рецензия
  архивируется вместе с текстом, связями и чужими реакциями; реакции не присваиваются другому тексту.
- Настройки типов, опыт знакомства, викторины и реакции дедуплицируются по своим предметным ключам.
  Дружба канонизируется, связь между двумя объединяемыми авторами удаляется; при совпадении
  сохраняется состояние основного, встречные заявки не превращаются в дружбу.
  Реакции, ставшие реакциями на собственную рецензию после переноса, архивируются и удаляются.
- Атрибуция media_items, franchises, media_item_franchises, багрепортов и предложений удаления
  связей переносится. Коллизия author_creation_request_id снимает только технический токен
  второй записи; сами записи общего архива не удаляются. Provider snapshots/links не меняются.
- Пароль и логин сохраняются у основного, при отсутствии переносятся из второго. Из двух
  identities одного провайдера остаётся основная, остальные провайдеры переносятся.
  Переносятся только подтверждённые email, существующий основной адрес имеет приоритет.
- Согласия второго архивируются с исходным автором как provenance; непересекающиеся факты
  переносятся, пересекающееся активное согласие остаётся историей закрытого автора.
- Уведомления автора переносятся; admin-уведомления с совпадающим числовым ID не затрагиваются.
- Выданные достижения объединяются по уровню. Старые перенесённые награды помечаются объявленными.
  Событие `author.accounts.merged` запускает полную переоценку новых достижений через consumer.
- Ledger основного аккаунта сохраняется на месте: ID, ключи, суммы и даты не переписываются.
  Только факты второго аккаунта проходят aliases оценок/рецензий и семантическую дедупликацию
  против основного. Совпадения и факты отсутствующих объектов второго архивируются и удаляются;
  остальные меняют владельца и ключи через `UPDATE ... FROM VALUES` пакетами по 500 строк.
  Разные события отказа модерации сохраняются отдельно. Все пакеты входят в одну транзакцию.
- XP/trust пересчитываются SQL-агрегатом только после фактического переноса новых фактов или
  при дополнительном историческом максимуме/административном подавлении второго аккаунта.
  Счётчики обновляются только при изменении значений, с сохранением created_at/initialized_at.
  При пустой истории второго аккаунта и отсутствии дополнительных ограничений/максимума
  история, XP, trust и временные метки основного вообще не изменяются. Производные строки
  закрываемого автора удаляются. Права доступа не повышаются объединением.
- Повторная reputation initialization разрешает старые author IDs через цепочки слияний
  и не создаёт проекции закрытым авторам. Live-consumer и initialization проверяют существующие
  награды/успешные исходы также по автору, действию и источнику: старые исторические ключи
  основного не меняются и не приводят к повторному начислению.

## Закрытый профиль и история

`authors.merged_into_author_id` — tombstone, запрещён self-reference. Старые публичные URL профиля
и достижений перенаправляются на конечного автора; поиск пользователей и действующие сессии
закрытого автора исключаются. Второй профиль не удаляется, исторические actor IDs остаются верными.
Конфликтующие live-строки удаляются после копирования в `account_merge_archive` (вместе с необходимыми
дочерними данными). Архив не имеет пользовательского API, не участвует в счётчиках и обработчиках.
Парольные хеши, session/challenge tokens и OAuth credentials в архив не записываются.
Исходный avatar object остаётся у tombstone/архива и не удаляется внешней best-effort операцией.

Сессии и access tokens обоих авторов отзываются, challenges потребляются. Новая сессия основного
выпускается в той же транзакции. Grant сохраняет result author/session и consumedAt; повтор
выполнения допускается только из актуальной сессии результата и не повторяет перенос/событие.
Старое initiating session после commit не даёт повторно войти, даже с прежним grant.

Dispatcher создаёт каноническую проекцию события в памяти, сохраняя исходный JSON/actor в БД.
События удалённых конфликтующих ratings/reviews погашаются без эффектов. Исторические payload,
job payload и audit не переписываются; DB guards запрещают stale workers создавать данные у
закрытого автора. Индекс архива `(table_name, entity_key)` защищает проверку от growing scan.

## Выпуск и проверка

Остановить старые приложение/workers, применить `0005_account_merge`, запустить обновлённый код.
Код со старой схемой или новая схема со старым worker не являются поддерживаемой комбинацией.
Миграция не объединяет существующих пользователей автоматически.

Интеграционные тесты используют `ACCOUNT_MERGE_TEST_DATABASE_URL` и отдельную временную схему,
применяют baseline и все миграции. Никогда не указывать application database. Сервисные тесты
используют `tests/fixtures/server-runtime.ts` для server-only boundary. Production build не нужен.

Проверка ограниченного объёма (изолированная PostgreSQL): по 1000 оценок у двух аккаунтов,
500 совпадений, итог 1500 оценок и 500 архивных конфликтов. Предпросмотр ~347 мс,
подтверждение ~2.02 с; это локальное измерение, не гарантия больших объёмов или production latency.
На этом наборе чтение двух авторов охватывает почти всю таблицу и закономерно использует seq scan;
на точечных fixture проверен bitmap owner index. Отдельно проверен план recursive historical facts.
Основной оставшийся предел — общий барьер и построчный перенос: большие архивы потребуют
set-based переноса и нового измерения до обещания масштабируемости.


Регрессия пустого OAuth-дубля проверяется на основном аккаунте с 6510 фактами: SQL-триггеры
в тесте запрещают любые INSERT/UPDATE/DELETE его ledger, progress и trust. Объединение проходит,
полные снимки строк остаются идентичными. Для двух заполненных аккаунтов проверены 5000 фактов,
сохранение ID/дат переносимых строк и полный rollback при ошибке второго UPDATE-пакета.
