# Редактор Creator: запросы и планы (2026-10-23)

Проверка выполнена в новой одноразовой БД PostgreSQL 17.2, созданной только для
теста и удалённой после него. Fixtures: 200 тыс. Creator (90% персон),
200 тыс. bindings, 1 млн именных mappings и 1 млн участий. Выполнен ANALYZE.
Тест: `tests/creator-editor-runtime.test.ts`, флаг `CREATOR_EDITOR_PERF=1`,
адрес только изолированной БД через `CREATOR_EDITOR_TEST_DATABASE_URL`.

## Изменение загрузки карточки

Вместо чтения всех Creator, mappings и creator_series с последующей JS-фильтрацией
читается Creator по PK и его связи по owner ID. Начальные варианты псевдонимов —
только уже выбранные участники. Нет полного каталога в HTML/RSC и клиентском поиске.

EXPLAIN (ANALYZE, BUFFERS): прежнее чтение всех Creator с сортировкой — 383–467 мс,
всех mappings — 117–153 мс (без учёта сетевой передачи и квадратичной JS-фильтрации).
Новая адресная карточка — 0,032–0,037 мс; history bindings — 0,032–0,034; mappings — 0,042–0,588;
DISTINCT ролей — 0,073; прямые серии — 0,008; исходящие отношения — 0,022;
входящие — 0,018–0,019; EXISTS-проверки зависимостей смены типа — 0,031–0,049 мс.
Проверка выбранного псевдонима для карточки — 0,031 мс; проверка типа владельца
FantLab binding с блокировкой Creator — 0,037 мс.
Существующие PK/owner/creator-role индексы обслуживают эти lookup; большого fan-out
карточки нет. Количество обращений фиксировано, не растёт на каждого кандидата.
Наследуемые серии используют прежний запрос и прежнюю семантику.

## Поиск участников псевдонима

Фактический SQL получен через `creatorRelationCandidatesQuery(...).toSQL()`.
Фильтры: person/collective, исключение самого Creator, нормализованные name OR
original_name; ORDER BY name,id LIMIT 21. 21-я строка — hasMore, в UI максимум 20.
Нет count(*) или offset; минимальная длина запроса 3, debounce 250 мс.

| Поиск | Без новых индексов, мс | После, мс |
| --- | --- | --- |
| Частый `creator` | 175–226 | 170–198 |
| Редкий `редкое имя` | 234–307 | 0,071–0,492 |
| Отсутствующий `неттакогоимени` | 234–341 | 0,055–0,069 |

Миграция 0140 добавляет два GIN trigram индекса, точно совпадающих с выражениями
normalizeSearchSql. Редкие/отсутствующие результаты используют BitmapOr индексных
поисков. Для широкого совпадения последовательный проход и сортировка остаются
оправданными: индексы не устраняют стоимость проверки почти всего набора. Выдача
ограничена, интерфейс предлагает уточнить запрос. JIT и коррелированных циклов
по всему набору для нового поиска нет. Добавляются только эти два индекса;
существующие exact identity и составные FK/индексы не меняются.

## Ограничения

Это синтетический сравнительный прогон, не SLA и не браузерный end-to-end тест.
Время зависит от кеша, CPU и распределения имён. Псевдонимы/серии в fixture малы;
основной масштаб — Creator, mappings, bindings и участия. Проверка manual save
и новых type/date guards выполнена на реальном PostgreSQL в том же runtime-тесте.
Планы текущего прогона сохранены в `/tmp/creator-editor-plans.json` вместе с SQL.
Production БД и сеть провайдеров не использовались.
