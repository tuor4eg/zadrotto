# Внешняя авторизация авторов

## Границы и источники истины

Внешний вход дополняет пароль и access token. `authors` остаётся единственным профилем,
`author_sessions` — единственной системой сессий автора. Авторизация администраторов независима.
`author_accounts` хранит парольный способ; внешнему пользователю не нужны фиктивные credentials.
Email внешнего сервиса не переносится в `author_emails`, не подтверждает локальный email и не
используется для поиска/объединения пользователей. Subject — непрозрачная строка с сохранением регистра.

`author_auth_identities` связывает пару provider/subject с автором; ограничения БД запрещают
владение одной идентичностью двумя авторами и несколько аккаунтов одного провайдера у автора.
Код provider стабилен в пространстве issuer/client конфигурации. Изменение пространства subject
требует отдельного кода или явной миграции: переиспользовать код для другого issuer/client нельзя.
Каталог контентных провайдеров и provider snapshots к авторизации не относятся.

## Подключение адаптера

Production-реестр `src/lib/auth/external/registry.ts` содержит адаптер Яндекс ID. Адаптер добавляется
серверным кодом и регистрируется в этом файле. Он объявляет протокол, публичное имя, допустимые
методы callback, состояние enabled/configured и точные HTTPS origins аватаров. Клиент получает
только code/name доступных провайдеров через `/author/auth/providers`.

`createOAuthAdapter` реализует Authorization Code + PKCE S256 и OIDC через oauth4webapi.
Метаданные issuer/endpoints доверенные, статические; произвольный issuer из запроса запрещён.
OIDC требует openid scope, JWKS, проверки подписи ID Token, issuer, audience/azp, сроков и nonce;
если используется UserInfo, его subject должен совпасть с ID Token. Алгоритм по умолчанию RS256,
иной разрешённый алгоритм задаётся явно. В OAuth2 адаптер предоставляет получение стабильного
subject по проверенному access token через свой API; email и nickname не заменяют subject.
Редиректы сетевого обмена запрещены; запросы ограничены по времени. Токены живут только в памяти
во время обмена. Не добавлять их в БД, cookie, activity log или Redis.

Для подписанного протокола реализуется тот же `start/verify` контракт, без требования code.
Такой адаптер обязан проверять подпись, назначение, срок и связь подписанного ответа с nonce
текущей попытки; если протокол требует отдельного replay key, он должен атомарно проверяться
адаптером в Redis до возврата identity. Непроверенный client payload нельзя возвращать как identity.
Из production-реестра нельзя экспортировать тестовые адаптеры или механизм их регистрации запросом.

Операционные переключатели и credentials управляются через `/admin/tools/auth`.
Серверный реестр асинхронно читает настройки; публичный контракт списка остаётся code/name.
`auth_provider_settings` хранит enabled и UUID revision, `provider_credentials` разделён по
назначению content/auth и коду. Контентные ciphertext v1 и мастер-ключ сохранены; auth v2
аутентифицирует назначение и код через AES-GCM AAD. Каталог полей и форма общие.

Попытка фиксирует revision. Callback проверяет её до и после внешнего обмена, а domain operation
удерживает FOR SHARE строки настроек до commit identity/session. Административное сохранение
берёт FOR UPDATE этой строки перед проверкой связанных аккаунтов и обновлением credentials.
Так исключаются commit на устаревшей конфигурации и смена Client ID одновременно с регистрацией.
Секрет можно ротировать; Client ID нельзя менять при существующих привязках.

Яндекс использует OAuth2 code + PKCE S256, Client Secret Basic и API `/info` с заголовком OAuth.
Subject берётся из id проверенного серверного ответа с совпадающим client_id; email не используется.
Запрашиваются только login:info/login:avatar. Тела ответов ограничены 64 КиБ, запросы — 10 секундами.
[Настройка, ручная проверка и согласованный выпуск](../YANDEX_ID.md).

## Временный обмен и CSRF

Начало: POST `/author/auth/[provider]/start`, с origin сайта из существующего SITE_URL.
Cookie привязки браузера HttpOnly, Secure в production, SameSite=None для cross-site POST callback,
Path=/author/auth. В локальном HTTP используется Lax; cross-site POST требует HTTPS.
Cookie не является сессией и не даёт авторизации. Каждая вкладка имеет независимый state.

Redis хранит попытку 10 минут: hash browser binding, provider, intent, state, verifier, nonce,
локальный returnTo; link дополнительно фиксирует author/session ID. Lua проверяет browser/provider
и удаляет попытку атомарно. Неверная привязка не сжигает чужую попытку. Повторный callback запрещён,
включая повтор после сбоя token endpoint: нужно начать вход заново. Redis недоступен — обмен закрыт.
Проверяются method, формат и размер callback. GET-провайдеры используют query, POST — form-urlencoded.
Callback URL отдельный для каждого провайдера и строится из SITE_URL; вместе с issuer validation
это защищает от mix-up. Возврат разрешён только на локальный путь. Ответы не кешируются.

Вход при действующей авторской сессии возвращает в профиль и не переключает автора. Привязка
проверяет ту же действующую сессию до обмена и повторно под блокировкой БД после него.
Внешний ответ не может выбрать локального автора: цель link берётся только из сохранённой попытки.

## Транзакции и доступ

Domain operation блокирует строку автора до изменения identity/session. Парольные мутации и
отзыв/удаление access token используют тот же порядок. Новый автор, identity и external-сессия
создаются одной транзакцией; конфликт уникальности откатывает лишнего автора и повторяет чтение.
Существующая identity ищется без фильтра blocked: блокировка не означает отсутствие аккаунта.
Cookie устанавливается только после commit, с существующими сроком и настройками авторской сессии.

Новый автор получает профиль доступа через resolveAuthorRegistrationAccessProfile и существующее
событие author.registration.submitted. Позднее добавление пароля не создаёт второй профиль или
повторный факт регистрации. pending_email ограничивает пароль, но допускает external/access_token
сессии. pending_approval, rejected, blocked и isSystem не допускают внешний вход.

Внешняя сессия хранит identity_id и provider. При отвязке под блокировкой автора повторно
проверяется сессия инициатора и наличие альтернативы: active пароль, неотозванный access token
или другая identity с настроенным включённым адаптером. Email, pending пароль и действующие сессии
альтернативой не являются. Затем сессии этой identity отзываются, identity удаляется; остальные
сессии сохраняются. Если отозвана текущая сессия, cookie очищается. Перед действием UI предупреждает
о завершении сессий и возможной необходимости входа на других устройствах, отдельно — о текущей.

Временно выключенный адаптер запрещает новые обмены, но сохраняет identities и сессии.
Удалённый адаптер оставляет недоступные identities. Оба не считаются рабочей альтернативой,
но не блокируют добавление других способов, onboarding и управление сессиями. Запрет применяется
только к отвязке, которая оставила бы профиль без работающего способа. При сетевой ошибке статус
адаптера не меняется; проверка альтернатив не обращается к внешнему сервису.
Административный отзыв access token остаётся административной операцией и может намеренно
лишить соответствующего способа входа; сам по себе он не отзывает существующие сессии.

## Имя и аватар

name_source_identity_id и avatar_source_identity_id независимы. Первая identity владеет обоими
полями, даже если сервис не вернул их значения. Повторный вход обновляет только поля её происхождения.
Link не меняет профиль. Ручное сохранение имени и загрузка/удаление аватара сбрасывают только
соответствующий источник, включая действия администратора. Avatar version защищает от применения
загрузки, начатой до ручного изменения или более свежей замены. Удаление identity сбрасывает ссылки
источников через FK SET NULL, значения сохраняются. Повторная привязка не включает обновление.

Аватар скачивается только с разрешённого адаптером HTTPS origin. DNS проверяется на публичный IPv4,
адрес закрепляется за соединением, редиректы запрещены; размер, время и декодирование ограничены.
Изображение преобразуется в WebP существующим sharp/MinIO стеком. Ошибка не отменяет вход.
После загрузки CAS проверяет источник и версию, заменённые/неиспользованные файлы удаляются best effort.

Фонового обновления, хранения токенов для него и UI выбора источников нет. Данные длительной
сессии могут устареть до следующего входа — это допустимое поведение первой версии.

## Миграция и проверки

0157_external_auth сохраняет пользователей и старые сессии. Дубликаты author/provider останавливают
миграцию с ошибкой; автоматически объединять или удалять их нельзя. Существующие имена и аватары
остаются локальными. provider/subject и author/provider индексированы уникальными ограничениями;
author sessions и source FK имеют индексы. Это точечные операции, масштабный benchmark не требуется.

Протокольные тесты используют реальные RSA-подписи с локальным HTTP mock, без настоящих провайдеров.
EXTERNAL_AUTH_TEST_DATABASE_URL и EXTERNAL_AUTH_TEST_REDIS_URL — только параметры тестовых запусков
на изолированных БД, не deployment-настройки. Production build для проверки не требуется.
