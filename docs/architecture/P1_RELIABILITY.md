# Надёжность фоновой обработки: P1

Реализация от 20 октября 2026 года. Изменения используют прежнюю очередь PostgreSQL и transactional outbox; новых таблиц, очередей, heartbeat и поколений событий нет.

## Владение выполнением

`guardSnapshotJob` проверяет `running`, token и срок аренды по часам БД, блокируя `job_runs` до завершения транзакции. После получения блокировки срок проверяется повторно. Ожидание блокировки ограничено, SQL и idle transaction получают timeout в пределах оставшейся аренды. `withSnapshotJobGuard` повторяет проверку перед завершением короткой транзакции. Сеть выполняется снаружи. Уже начатая транзакция сериализуется с recovery; это не обещание физически остановить SQL ровно в момент deadline.

Guard передаётся через существующий контекст в точки фиксации метаданных/snapshots, платформ/логотипов, заявок, создателей и их изображений, частей/миниатюр, аниме, AI-справок, наград, репутации, статистики, очисток и экспортов. Защищены также записи ошибки, checkpoints и продолжения. `succeeded` отклоняется после истечения аренды. Email и транспорт уведомлений дополнительно используют собственное владение сообщением: подтверждение уже выполненной доставки не выводится только из состояния родительского job.

CSV загружается под уникальным ключом попытки; публикация результата и ошибки защищена guard. Запоздавший исполнитель не перезаписывает файл новой попытки. Общие content-addressed изображения не удаляются только потому, что один исполнитель потерял аренду.

Источники: [guard](../../src/db/queries/provider-snapshots.ts), [jobs](../../src/db/queries/jobs.ts), [registry](../../src/lib/jobs/handlers.ts), [CSV](../../src/lib/admin-exports/generate.ts), [тесты записей интеграций](../../tests/worker-integration-fencing-runtime.test.ts).

## Email и безопасный переход

Claim выдаёт новый `lease_token` и увеличивает attempts. Срок по-прежнему определяется `updated_at` и 15 минутами; перед каждой отправкой проверяются отмена и аренда. Completion обновляет только непросроченный `sending` с соответствующим token, очищает его и возвращает boolean. Устаревший ответ не меняет состояние и не считается доставкой.

Ключ Resend остаётся ID письма плюс хеш отправляемого тела. Одинаковый запрос получает прежний ключ независимо от token аренды. Resend сохраняет ключи **24 часа**, поэтому это не бессрочная exactly-once гарантия. Изменение sender, reply-to, шаблона, SITE_URL или аккаунта может нарушить предпосылки безопасного повтора. [Условия Resend](https://resend.com/docs/dashboard/emails/idempotency-keys), [транспорт](../../src/lib/auth/resend.ts).

Перед миграцией выполнить read-only отчёт:

```sh
NODE_PATH=./node_modules/next/dist/compiled NODE_OPTIONS=--conditions=react-server \
  ./node_modules/.bin/tsx tools/check-email-lease-cutover.ts
```

Команда работает и до появления новой колонки, не выводит секреты, тело письма или ключ. Ненулевой exit code означает, что готовность не подтверждена; это не разрешение автоматически сбросить `sending`.

В текущей модели историческое отправленное тело/ключ не сохраняются. Поэтому миграция `0129` консервативно переводит все legacy `sending` в существующий `failed` с понятной причиной неизвестного исхода. ID, attempts и payload сохраняются. Она не возвращает их автоматически в очередь. Перед явным операторским повтором нужно проверить прежний запрос/аккаунт и окно идемпотентности; возраст строки менее 23 часов — только консервативное условие времени, не доказательство неизменности тела. Автоматического исключения по возрасту в миграции нет.

Источники: [outbox](../../src/db/queries/email-outbox.ts), [delivery](../../src/lib/auth/email-outbox-delivery.ts), [preflight](../../tools/check-email-lease-cutover.ts), [миграция](../../drizzle/0129_email_outbox_lease.sql).

## Восстановление автомодерации

Отдельная аренда check не создаётся. Проверка принадлежит запуску `moderation.auto-check`; при записи сверяются job type, `checkId`, token и срок. Порядок блокировок — job → check → запись. Терминальный результат не переоткрывается старым исполнителем или ошибкой activity log.

Истечение единственной попытки приводит к `completed / NEEDS_REVIEW`, сохраняя ручную модерацию. В прежнем recovery-проходе ограниченная сверка находит незавершённые проверки без queued/running job, в том числе при уже удалённой истории. Ручной retry сериализуется с этой сверкой и не переоткрывает терминальное решение. Успешное одобрение, зафиксированное до аварии worker, сохраняется вместе с событиями.

Источники: [recovery](../../src/db/queries/automoderation-recovery.ts), [process](../../src/lib/automoderation/process.ts), [approval](../../src/lib/automoderation/media-policy.ts), [интеграция с jobs](../../src/db/queries/jobs.ts).

## Продвижение событий и диагностика

В `domain_event_outbox` добавлено только `next_attempt_at`. Допуск короткой транзакцией сохраняет отсрочку 60 секунд до запуска consumers. Авария после допуска не возвращает событие сразу в начало. Recovery выбирает готовые события по `(next_attempt_at, event_id)`; блокировки пропускаются через SKIP LOCKED. Immediate dispatch использует тот же допуск.

Consumer effects, consumption marks и `dispatched_at` по-прежнему фиксируются одной транзакцией. После ошибки отсрочка pending-события продлевается монотонно от времени ошибки. Неизвестные типы не удаляются. Отложенные и занятые события не считаются ошибками.

Каждая фактическая ошибка записывается в существующий activity log как failure/warning с event ID, типом, run ID, consumer, безопасным error code, возрастом и следующей попыткой. Payload и сырые SQL-ошибки не записываются. Батч продолжает остальные события, после чего job завершается failed со ссылкой на `/admin/activity`, без собственного автоматического retry этой сводной ошибки: повтором управляет outbox. При недоступности activity log остаются системный лог и журнал запуска.

Фиксированная пауза управляет **новыми допусками**, а не является строгим лимитом «одно выполнение раз в 60 секунд». Ранее допущенный живой исполнитель может вернуться после другой неуспешной попытки; блокировка и транзакционная идемпотентность сохраняют корректность без поколения. Успешное событие повторно не применяется.

Источники: [dispatcher](../../src/lib/domain-events/dispatcher.ts), [handler и сводка ошибок](../../src/lib/jobs/handlers.ts), [миграция](../../drizzle/0130_domain_event_recovery_backoff.sql).

### Масштаб SQL-проверок

| Контур | Синтетический объём | Проверено |
| --- | --- | --- |
| Email | 120 600 строк, включая 120 000 sent/failed и различные pending/sending | Старый и новый claim, quarantine, exhausted, PK validation/completion и preflight. Архив не просматривается для каждого письма; per-send validation ограничена размером батча. |

Очень большой активный backlog и недоступность внешних сервисов остаются эксплуатационными ограничениями, а внешняя доставка не получает абсолютную exactly-once гарантию.

## Текущие задачи и остановка

`/admin/tools/jobs/current` показывает все queued/running запуски (ручные, по расписанию и от событий) с пагинацией по 50, выполняющиеся первыми. Счётчики и страница читаются в одной read-only repeatable-read транзакции. Обновление RSC выполняется каждые 5 секунд только в видимой вкладке, в том числе при пустом списке; при возвращении во вкладку — сразу. Завершённые запуски остаются в журнале. Расписания без активного запуска находятся на отдельной вкладке.

Проекция прогресса читает только известные числовые counters из payload/checkpoint/profileCheckpoint; raw payload в UI не выводится. ID курсора/throughId не являются общим количеством работы. Для неизвестного объёма показывается неопределённый progressbar; отдельные этапы синхронизации платформ не выдаются за общий процент. Профильный обход по bindings и missing-only выборка не используют число Creator как число профилей. Задачи без сохранённых counters показывают статус и время без выдуманной статистики.

`cancelJobRun` отменяет queued и running любого типа, атомарно очищает ownership и сохраняет checkpoint. Старый queued-only helper остаётся queued-only. Worker проверяет ownership перед каждым handler и раз в секунду; metadata search/fetch получает AbortSignal, циклы проверяют его до persistence и между записями. Уже сохранённое не откатывается; расписание и отдельно созданные дочерние runs не отключаются. Уже начавшийся внешний эффект может завершиться: email/outbox completion сохраняет собственные leases и идемпотентность.

Отмена в той же транзакции согласует незавершённый экспорт (queued/running → failed) и initializing репутации (→ disabled), не меняя ready экспорт или enabled систему. Для экспортов общий порядок блокировок — job_runs → admin_exports, включая старую queued-only отмену на странице экспорта. Начало расчёта репутации и enqueue теперь атомарны; новый расчёт не начинается, пока queued/running предыдущего ещё существует. Это исключает сброс новой инициализации отменой прежнего run. Автомодерация использует прежний reconcile.

Индекс миграции `0137_current_jobs`: `(status DESC, created_at, id) WHERE status IN ('queued','running')`. На изолированной PostgreSQL проверены фактические Drizzle SQL и планы до/после: 500 тыс. завершённых запусков и ~1000 active, ANALYZE, обычная/глубокая/пустая страница, counts и связанные lookup отмены/инициализации. До индекса чтения просматривали историю (~25–43 мс на локальном стенде), после используют partial index: count ~0,25 мс, первые 50 ~0,07 мс, глубокая страница ~0,5 мс. Это SQL-измерения, не SLA. Count и OFFSET растут с активным backlog; очень большая очередь требует отдельной проверки. Отмена/согласование записей проверены EXPLAIN без исполнения benchmark-записей; функциональные и конкурентные тесты работают только на синтетических данных.

Проверки: `tests/current-jobs-runtime.test.ts`, `tests/current-job-progress.test.ts`, worker/metadata cancellation tests. Дополнительных env vars или нового статуса/механизма очереди нет.


## Каталог операций и исторические миграции

`catalog.ts` задаёт ручное размещение general/domain/migration/none. Общая форма не перечисляет все исполняемые handlers; server actions независимо проверяют placement. Миграции имеют отдельную вкладку, типизированные формы, последний запуск и ссылку на журнал с фильтром type. Если зарегистрированных миграций нет, страница показывает «Сейчас нет доступных миграций». Новая миграция добавляется обычным handler и явными метаданными формы/назначения в каталог, без универсального JSON-редактора. Активные запуски всех размещений используют прежние current/lease/retry/cancel.

Администратор подтвердил полную обработку production-данных. Семь исторических переносов (companies/directors TMDB, BGG, игровые компании, старые FantLab bindings, книжный legacy, глобальный genre-series) удалены из реестра вместе с их оболочками. Каталог миграций теперь пуст; вкладка остаётся для будущих переносов. Исторические названия сохранены в retired-каталоге, новые запуски и retry запрещены. Обычные импорты, автоапрув, идентичности и предметные операции сохранены. История с retention сама по себе не была доказательством завершённости.

Три старых массовых типа изображений сняты с эксплуатации; targeted действия используют общий creator-image-refresh с выбранным binding. Registry возвращает job-type-retired без retry; журнал сохраняет название, скрывает кнопку повтора и server-side retry запрещён. Уже начатые старые workers должны быть остановлены до выкладки: код не преобразует исторические checkpoints в новые задания.

Расписания сохраняют существующий payload при редактировании; поля metadata fill/refresh, thumbnails и rating reconciliation показывают сохранённые значения. Остальные payload сохраняются сервером при omission. Число 13 разрешённых периодических типов не изменено. Текущие cron/enabled автоматически не переписываются.

Расчёт репутации требует marker атомарного предметного действия и действующий guard. Dedicated enqueue advisory 90420262 сериализует обычные и recovery-запросы до active-run проверки. Workers и cancel этот ключ не захватывают; их порядок run → settings сохраняется. Cleanup требует initializing и подтверждённого владельца; stale/невалидный запуск не отключает enabled. Legacy {} не авторизуется автоматически. После его остановки/завершения orphaned initializing восстанавливается отдельной кнопкой в настройках, без изменения сохранённой конфигурации. При активном расчёте восстановление отклоняется.

Для жанра добавлено предметное применение заменяющей серии: только опубликованные записи выбранного активного жанра, keyset-партии по 25 с фиксированным throughId, существующие ручные связи сохраняются. Повтор безопасен: вставки идемпотентны, current genre/series перечитываются под прежними блокировками. Глобальная оболочка переноса удалена; применение требует конкретный genreId и ограниченную keyset-партию.

Проверка запросов: фактический SQL новых latest migration probes и scoped genre keyset компилируется в tests/job-migration-query.test.ts. Latest uses unnest(types) + lateral ORDER BY created_at DESC,id DESC LIMIT1: существующий job_runs_type_created_idx ограничивает probe одним типом, возможна дополнительная сортировка совпавших timestamps. Журнал уже поддерживал type-предикат; новая ссылка использует его для count и pagination (type_created index, отдельная сортировка active-first). Genre scope использует media_items PK/keyset, media_item_genres PK/genre index и существующую recursive membership проверку, без размножения строк. Новые reputation lookup/update адресны по PK, ограничения unique active init сохранены. Новых индексов без измерений не добавлено.

Ограничение проверки: EXPLAIN/ANALYZE и измерения на представительной изолированной БД не выполнялись после прежнего отказа доступа. Выполнены unit/runtime-with-mocks, SQL compilation, typecheck и lint; DB concurrency и планы не считаются подтверждёнными. Перед крупным переносом проверить latest/count/pagination на 1 млн runs разных типов и жанровую выборку на 100 тыс. записей/1 млн связей с популярным, редким и отсутствующим жанром, ANALYZE; сравнить работу/loops/buffers с прежними запросами. Без выполнения записей ради benchmark.

Выкладка: остановить scheduler/workers, проверить active/legacy init runs и завершённость переносов, выложить код, затем запустить процессы. Миграция 0139 удаляет только индекс уникальности старой игровой задачи и две её checkpoint-таблицы. Она отказывается выполняться при active runs любого из семи переносов или незавершённых игровых checkpoints; доменные данные и job history не удаляет. Код новых workers выкладывать при остановленных старых процессах. Миграция в этой сессии к БД не применялась.


## Удаление расписаний

Администратор удаляет расписание по ID с подтверждением ID и кода в UI. Операция блокирует
строку `jobs` в том же порядке, что и scheduler claim; scheduler использует `SKIP LOCKED`.
Запись `job.deleted` и удаление выполняются в одной транзакции. Существующий FK
`job_runs.job_id → jobs.id ON DELETE SET NULL` сохраняет завершённые и активные runs,
payload/checkpoint и ownership. Удаление не отменяет уже созданные запуски. Их история
остаётся в общем журнале и далее подчиняется срокам хранения запусков без расписания.
Имена/ID удалённого расписания сохраняются в административном activity log; run сохраняет
свой тип и источник. В текущих задачах источник `schedule` без владельца показан как
«Удалённое расписание», а null-job фильтр журнала называется «Без расписания».

Проверка: `tests/job-schedule-delete-runtime.test.ts` на отдельной PostgreSQL 17 — сохранение
всех статусов/payload, атомарный rollback при ошибке audit, повторное удаление, соседнее
