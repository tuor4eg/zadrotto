# Архитектурные инварианты

Правила ниже выведены из фактических путей записи и ограничений на 20 октября 2026 года. Для каждого указано место реализации. Часть гарантий обеспечена PostgreSQL, часть — только общими серверными функциями: прямой SQL обязан повторять эти правила. Известные ограничения не следует считать автоматически исправленными; они перечислены в [TECH_DEBT.md](TECH_DEBT.md).

## 1. Общий архив и авторский вклад

- `MediaItem` — единая запись архива. Тип и носитель не создают отдельного владельца или отдельную основную сущность. `created_by_author_id` — атрибуция вклада. Автор редактирует и удаляет собственные `private/rejected`, а после публикации общими данными управляет администратор. [Публикация](../../src/lib/authors/media-publication.ts), [операции записи](../../src/db/queries/media-items.ts), [продуктовые границы](../../PROJECT_CONTEXT.md).
- Публикация записи, серии и связи запись–серия проверяется отдельно. Нельзя выводить публичную принадлежность только из существования строки junction-таблицы. Для ветки дерева учитываются опубликованные узлы и опубликованные связи. [Общая проверка принадлежности](../../src/db/queries/series-membership.ts), [серии](../../src/db/queries/franchises.ts).
- Рецензия и её оценка принадлежат автору. Модерация меняет публикацию и административную заметку, не переписывает авторский текст или оценку. `contributions` сейчас имеет только `review`; не считать каркас поддержкой произвольных материалов. [Операции рецензий](../../src/db/queries/contribution-reviews.ts), [модель вкладов](../../src/lib/contributions/model.ts).
- Режим demo — локальные данные устройства, не серверная авторизация. Серверные действия опираются на сессию и проверенного автора. При импорте demo существующие серверные данные имеют приоритет: импорт не перезаписывает занятые оценки/статусы; доступны только опубликованные записи разрешённых типов и допустимые части. [Проверка сессии](../../src/lib/auth/author-auth.ts), [транзакционный импорт](../../src/db/operations/demo-profile-import.ts).
- Доступность типа и пользовательский выбор различаются: `accessible` определяется публичностью типа и правами гостя/профиля, `enabled` дополнительно применяет предпочтение автора или значение по умолчанию. Отключённый в фильтрах тип не равен запрещённому типу; предпочтение не выдаёт прав доступа. [Оба уровня запросов](../../src/db/queries/media-types.ts), [вычисление предпочтения](../../src/lib/media/types.ts).

## 2. Происхождение данных и ручные решения

- Переход провайдера на raw-снимки обязан сохранять контракт потребителей, а не только полный JSON. Для формы отдельно проверяются название, оригинальное название, год и описание по всей цепочке raw → проекция → metadata fields → форма; неполные метаданные дополняют выбранный результат, не очищают его. Полный ответ в JSONB и тест только авторов не доказывают совместимость формы. При новом переходе расширять [контрактные тесты](../../tests/provider-title-fields-contract.test.ts) и проверять offline replay/режим без обогащения редакционных полей.

- Сырые ответы провайдеров, рабочие отношения и редакционные данные — разные слои. Raw-снимок не является разрешением публиковать или заменять ручные значения. Для нормализованных книг авторы/издатели публичной формы метаданных строятся из рабочих отношений, язык хранится в `facts.originalLanguage`; payload снимка не читается. [Книжные проекции](../../src/db/queries/book-metadata.ts), [запись метаданных](../../src/db/queries/media-item-metadata.ts).
- Для фильмов TMDB внешние жанры служат доказательством в raw-снимке, а рабочие внутренние жанры — в `media_item_genres`. `facts` не дублирует внешние имена/ID или внутренние ID. Сопоставление и повторное применение модерации читают снимок текущего источника; отсутствие снимка после очистки не трактуется как пустой список жанров. [Проекция](../../src/lib/providers/tmdb-film-adapter.ts), [модерация](../../src/db/queries/genre-requests.ts).
- Провайдерная синхронизация жанров/платформ сохраняет `is_manual`: исчезнувшая внешняя связь удаляется только без ручного признака; иначе снимается `provider`. `provider` здесь один, это не многопровайдерный ledger. [Жанры](../../src/db/queries/media-item-genres.ts), [платформы](../../src/db/queries/media-item-platforms.ts).
- Связь создателя сохраняется, пока у неё есть ручной признак или хотя бы одна `entry_creator_sources`. Источники разных имён/провайдеров не следует сворачивать в один boolean. При ручном сохранении меняется ручной слой, затем удаляются только оставшиеся без источников автоматические связи. [Ручные связи и prune](../../src/db/queries/creators.ts), [синхронизация sources](../../src/db/queries/creator-requests.ts).
- Отказ от сопоставления — сохраняемое решение `provider_*_exclusions`, а не отсутствие данных. Новое получение того же значения должно учитывать его; повторное открытие производится явной административной операцией. Уже принятое решение не равно завершённому применению: отдельно проверять состояние задания. [Жанровые заявки](../../src/db/queries/genre-requests.ts), [платформенные заявки](../../src/db/queries/platform-requests.ts), [заявки создателей](../../src/db/queries/creator-requests.ts).
- Ручные и импортированные ассеты имеют происхождение, хеши и версии. Обновление внешнего профиля не следует трактовать как команду заменить ручное изображение. [Аватары создателей](<../../src/app/admin/(protected)/creators/avatar-actions.ts>), [логотипы платформ](<../../src/app/admin/(protected)/platforms/logo-actions.ts>).

Приоритет ручных решений не является универсальным механизмом блокировки всех полей записи: у разных подсистем разные признаки (`is_manual`, provenance, выбранный псевдоним, `locked` у summary). При изменении конкретного поля нужно проверить именно его путь записи. [Схема](../../src/db/schema.ts), [метаданные](../../src/db/queries/media-item-metadata.ts).

## 3. Полиморфные снимки

- Тип доменной цели регистрируется серверным кодом; сейчас встроены `media-item` и `creator`. Нельзя принимать SQL-таблицу или произвольный тип сущности из запроса. ID канонизируется и проверяется реестром. [Реестр](../../src/lib/providers/entities.ts).
- Attach/delete/merge должны блокировать целевую сущность и менять её snapshot links в той же транзакции через общие функции. Авторская привязка разрешена только к собственному черновику/отклонённой записи; к создателю автор не получает такой доступ. [Права и lock](../../src/lib/providers/entities.ts), [общие операции](../../src/db/queries/provider-snapshots.ts).
- На доменную цель `provider_snapshot_links` нет обычного FK. Поэтому миграции, импорты, удаление и перенос сущностей обязаны явно удалить или перенести links атомарно. Удаление одной внутренней сущности не должно уничтожать общий снимок, используемый другими целями. [Схема](../../src/db/schema.ts), [удаление записи](../../src/db/queries/media-items.ts), [удаление создателя](../../src/db/queries/creators.ts).
- Проверять версию/хеш snapshot references при применении подготовленного результата; проверять guard задания до изменения рабочих данных и сохранять checkpoint согласованно с результатом. Снимок мог обновиться, пока выполнялись внешние запросы. [Проверки снимков](../../src/db/queries/provider-snapshots.ts), [атомарное применение метаданных](../../src/db/queries/media-item-metadata.ts).
- `media_item_provider_snapshots` нельзя удалять как «дублирующий raw-кеш»: это отдельное доказательство исходных данных для автомодерации предложения. Его удаляют пути ручного и автоматического одобрения submitted-заявки; универсальной очистки при любом переходе в published нет. Оно не заменяется автоматически `provider_snapshots`. [Автомодерация](../../src/lib/automoderation/media-policy.ts).

## 4. Транзакции, блокировки и повторная доставка

- Импорт/синхронизация сначала блокирует родительскую `media_items`, затем ключи заявок в стабильном порядке. Транзакция принятия решения блокирует заявку и создаёт задание, не обходя записи с обратным порядком блокировок. Применение выполняется отдельным заданием по затронутым записям. Это предотвращает дедлоки «запись → заявка» / «заявка → запись». [Порядок для жанров](../../src/db/queries/genre-requests.ts), [для платформ](../../src/db/queries/platform-requests.ts), [для создателей](../../src/db/queries/creator-requests.ts).
- Бизнес-изменение и соответствующее событие записываются в одной транзакции. Непосредственный dispatch инициируется после commit; durable outbox нужен, даже если немедленная постановка задания не удалась. Не заменять это вызовом внешнего транспорта внутри доменной транзакции. [Обёртка транзакции](../../src/db/transaction.ts), [запись событий](../../src/lib/domain-events/persistence.ts).
- Повторная доставка ожидаема. Для потребителя действует отметка потребления, для награды репутации — отдельный уникальный ключ источника, для исхода решения — свой ключ. Нельзя выдавать XP только потому, что событие повторно дошло до обработчика. [Репутация](../../src/lib/reputation/service.ts), [ограничения ledger](../../src/db/schema.ts).
- Права определяются серверным профилем доступа, а не XP, demo-данными или видимостью кнопки. Автоповышение доверия учитывает блокировку и ручной запрет; оно не выдаёт административных полномочий. [Профили](../../src/lib/authors/access-profiles.ts), [репутация](../../src/lib/reputation/service.ts).
- Результат автомодерации применяется только к прежнему `submitted` с ожидаемыми `moderation_revision` и `updated_at`, при отсутствии новых неопубликованных серий. Нельзя одобрять изменившуюся заявку по старому результату. [Проверка и условное применение](../../src/lib/automoderation/media-policy.ts).

## 5. Серии, части и редакционные ссылки

- Дерево серий не должно содержать циклы или превышать настроенную глубину. PostgreSQL запрещает только непосредственную ссылку на себя; полный обход и сериализация изменений находятся в серверной операции. При переподчинении действует общий advisory lock и удаляются избыточные прямые связи с предками. Прямой UPDATE `parent_id` обходит эти гарантии. [Обновление серии](../../src/db/queries/franchises.ts).
- В одной ветке хранить наиболее конкретную прямую связь записи, а принадлежность к предкам получать через ветку. Не добавлять ancestor links как «кеш» без пересмотра семантики. [Нормализация выбранных серий](../../src/db/queries/media-items.ts), [публичные ветки](../../src/db/queries/series-membership.ts).
- В архиве выбранная серия по умолчанию включает опубликованных потомков. Режим `seriesChildren=0` учитывает только прямые опубликованные связи; список, пагинация и счётчики типов используют один фильтр. Переключатель доступен при наличии видимых потомков и не меняет сами связи.
- `replacement_franchise_id` у жанра меняет публичную видимость при принятой принадлежности к опубликованной ветке; не означает физического удаления жанра или автоматического принятия связи. [Правило видимости](../../src/db/queries/media-item-genres.ts).
- Часть принадлежит ровно одной записи. Ссылка из оценки/рецензии должна совпадать по `(media_item_id, part_id)`; уникальны тип/номер и пара провайдер/внешний ID внутри записи. ID части нельзя пересоздавать без учёта пользовательских ссылок. Исчезновение части из ответа не команда удалить историю. [FK и уникальность](../../src/db/schema.ts), [синхронизация](../../src/db/queries/title-parts-sync.ts).
- Спецвыпуск `season:0` не получает новых оценок и рецензий; исторические оценки исключаются из эффективного голоса. [Правила частей](../../src/lib/media/title-parts.ts), [эффективные оценки](../../src/db/queries/effective-ratings.ts).
- В редакционных документах учитывать обе формы ссылки: одиночный `media` и элементы `entry_group`. При сохранении блоков блокировать документ и проверять опубликованность записей; при снятии публикации/удалении записи учитывать редакционные ссылки. FK `restrict` не заменяет проверку статуса публикации. [Запись блоков](../../src/db/queries/editorial-documents.ts), [общий подсчёт ссылок](../../src/db/queries/editorial-document-references.ts), [операции записи](../../src/db/queries/media-items.ts).

## 6. Создатели и идентичность

- Ручная пара календарных дат Creator имеет смысл рождения/смерти для `person` и создания/закрытия для `organization`; порядок дат проверяется одинаково. Организационные даты не заполняются из персональных профилей. У исходящего персонального псевдонима даты жизни недоступны.
- Тип Creator нельзя менять обычным сохранением, пока существуют активные внешние ID, именные mappings, участия, связи псевдонима или импортированное изображение. Это предметная проверка под блокировкой Creator; ошибки не должны маскироваться под конфликт slug.
- В редакторе внешние ID и именные mappings различаются. Исторические bindings показываются отдельно по статусу, не используются для получения профиля/изображения и не удаляются ради возможности удалить Creator. Новые сопоставления провайдеров проходят существующие предметные операции/модерацию.
- Редактор одного Creator загружается адресно. Поиск участников псевдонима выполняется на сервере с общей нормализацией, ограниченной выдачей и защитой от устаревших ответов; полный каталог в форму не передаётся.

- Компании фильмов TMDB идентифицируются как `tmdb / company:<ID>`, имеют тип organization и роль production_company. Регистрация заявок/источников и удаление хранимого `facts.productionCompanies` атомарны; отсутствие или повреждение snapshot не равно пустому составу. Автоапрув использует обычное решение и job применения, сохраняет исключения и ручное переоткрытие. Логотип — отдельное обогащение: сеть не нужна для replay/апрува, ручной avatar и avatar другого провайдера не заменяются. [Синхронизация](../../src/db/queries/tmdb-companies.ts), [jobs](../../src/lib/creators/tmdb-company-jobs.ts), [логотипы](../../src/lib/creators/tmdb-company-images.ts).

- Даты жизни FantLab заполняют только пустые `birth_date`/`death_date` у персоны без исходящей `pseudonym_of`; даты псевдонима не распространяются на участников. Заполненные даты сохраняются независимо от происхождения, ручное очищение разрешает повторное автозаполнение. Полные календарные даты и их порядок проверяются до записи; сеть не выполняется под блокировкой Creator. Под guard задания перечитываются привязка и eligibility, проверяется хеш снимка, а даты, links и checkpoint фиксируются одной транзакцией. [Правила дат](../../src/lib/creators/life-dates.ts), [транзакционное применение](../../src/db/queries/creator-provider-snapshots.ts).

- Внешний ID осмыслен только вместе с провайдером и пространством ресурсов. `rawg developer:N` и `publisher:N` — разные идентичности, даже при одинаковом числе. Активная внешняя идентичность принадлежит одному внутреннему создателю; mapping/source с binding должен ссылаться на того же создателя и провайдера через составной FK. [Схема](../../src/db/schema.ts).
- Неоднозначное совпадение имени не основание автоматически объединить создателей. Автоматические BGG/IGDB/RAWG решения имеют отдельные ограничения по типу и конфликтам ID; вручную переоткрытая заявка не должна автоматически закрываться тем же правилом. [Решения заявок](../../src/db/queries/creator-requests.ts).
- Псевдоним — направленное `pseudonym_of`; отображение и фильтры используют непосредственные связи. Не вводить неявное обратное или транзитивное раскрытие. При выборе псевдонима проверяется наличие всех связанных авторов в роли writer у записи. Последующее изменение состава не снимает выбор автоматически: UI предупреждает о неполноте. Это проверка пути выбора, не постоянный SQL constraint полноты состава. [Создатели и псевдонимы](../../src/db/queries/creators.ts).

## 7. Оценки и совместимость чтения

- У Creator одна публичная страница для всех типов медиа. Вкладки отражают опубликованные доступные записи по общей принадлежности Creator и непосредственных псевдонимов, не текущий поиск, роль или другие фильтры. `type` хранит выбор в URL; без него выбран «Все». Доступность типа проверяется независимо от пользовательского предпочтения отображать его в обычном архиве. [Страница](../../src/app/archive/page.tsx), [общая принадлежность и типы](../../src/db/queries/creators.ts).
- Публичные компании перенесённых фильмов TMDB читаются из рабочих участий и зарегистрированных заявок; raw-снимок не служит источником рендеринга. Ссылка требует рабочего участия, ожидающая заявка даёт подпись, исключённый автоматический источник скрыт. Ручное участие не скрывается из-за исключения источника. Совместимый `facts.productionCompanies` в read DTO вычисляется для summary/экспорта и не является сохраняемым JSON; legacy fallback действует только пока ключ остаётся в хранимом `facts`. [Проекция чтения](../../src/db/queries/tmdb-company-display.ts), [read DTO](../../src/db/queries/book-metadata.ts).

- Явные оценки — только целые `10…100`, кратные 10. Эффективная оценка автора — общая оценка либо среднее оценок частей, но не сумма голосов каждой части. Дробный результат вычисления не становится новой явной оценкой. [Ограничения](../../src/db/schema.ts), [общая формула](../../src/db/queries/effective-ratings.ts).
- Агрегат `media_item_rating_stats` — производные количество и сумма эффективных голосов. Новые пути изменения рейтинга должны сохранять его согласованность или явно пересчитывать его; нельзя читать его как независимо вводимые данные. [Операции агрегата](../../src/db/queries/media-item-rating-stats.ts).
- Пустое значение и отсутствие поля различаются. Например, `description: undefined` в синхронизации части сохраняет прежний перевод, тогда как переданное значение обновляет его; авторы/издатели в нормализованных книжных `facts` являются совместимой формой чтения из связей, а в хранимом JSON остаётся язык (`originalLanguage`) или `{}`. [Контракт части](../../src/lib/media/title-parts.ts), [синхронизация](../../src/db/queries/title-parts-sync.ts), [книжное чтение](../../src/db/queries/book-metadata.ts).
- Поиск по пользовательскому тексту использует общие `normalizeSearchText` и SQL-эквивалент. Индекс должен соответствовать реальному выражению; собственный `lower`/`ILIKE` меняет семантику. Технические идентификаторы не нужно нормализовать как текстовые названия. [Нормализация](../../src/lib/search/normalize.ts), [SQL и индексы](../../src/db/search.ts).

## Проверка существенных изменений

При изменении доменной связи проверять не только её форму записи, но также публичные фильтры, модерацию, повторное применение провайдера, удаления/слияния, производные данные и восстановление после сбоя. Проверки схемы не покрывают все перечисленные правила. Новые/изменённые запросы требуют анализа SQL, плана и репрезентативного масштаба по [AGENTS.md](../../AGENTS.md); этот документ не является результатом нагрузочного измерения.

## Владение фоновой работой и recovery

- Начальная и финальная проверка job token/DB-clock lease выполняются в транзакции доменной записи; checkpoints, ошибки и продолжения подчиняются тому же владению. Сеть находится вне транзакции. Уже завершённый результат не переписывает старый исполнитель.
- Email completion требует непросроченный token сообщения; старые sending без доказанного исхода не возвращаются автоматически в очередь при cutover.
- Осиротевшая автомодерация завершается как NEEDS_REVIEW существующим recovery; терминальные решения не переоткрываются неявным retry.
- Pending-событие не удаляется из-за повторных ошибок. Сохраняемый next_attempt_at обеспечивает продвижение, effects/consumptions/dispatched остаются атомарными; ошибки видны в activity log и журнале jobs.

Источники, тесты и границы гарантий: [P1_RELIABILITY](P1_RELIABILITY.md).

### Raw-профили Creator

- Получение профиля по внешней идентичности не требует локального Creator и не изменяет его рабочие поля. Автоматическое связывание разрешено только для загрузки по подтверждённому binding с повторной проверкой владельца, активности, дескриптора и hash под блокировкой цели.
- При смене binding сохраняется независимый raw, но не создаётся связь со старым владельцем. Существующие links других источников не удаляются. Связь и checkpoint job фиксируются атомарно с проверкой lease через общие helpers.
- «Только без снимков» использует полный дескриптор адаптера: рабочий кеш не считается raw; полный сохранённый профиль переиспользуется без сети. Этот режим не создаёт Creator, заявки модерации или рабочие связи.

### Режиссёры фильмов TMDB

- Только `film` и `credits.crew[job='Director']` полного снимка текущего movie-источника создают участия `person / director`. Идентичность — `tmdb / person:<ID>`; она независима от `company:<ID>`. Отсутствующий/повреждённый crew не является пустым составом. Валидный пустой состав снимает только автоматические TMDB-основания роли director, сохраняя ручные и остальные sources.
- Автоапрув персоны сопоставляет только подтверждённый активный ID. Без него совпадение имени, originalName или сохранённого варианта любого провайдера требует модерации. Неактивная прежняя привязка, исключение и ручное переоткрытие не восстанавливаются автоматически. Решение и применение остаются отдельными транзакциями/jobs; компании обрабатываются только в namespace company.
- TMDB person raw хранится в общих snapshots (`person.details`, `language=ru-RU`), его получение и link не применяют поля. Отдельная обработка заполняет только пустые календарные даты с существующими правилами псевдонимов; имена/описания не обновляет. Под Creator lock binding удерживается `FOR SHARE`, snapshot hash и lease проверяются перед записью.
- Портрет берётся из сохранённого связанного person snapshot отдельным job. Ручной аватар и аватар другого источника/внешнего ID не заменяются; отсутствие profile_path не удаляет изображение. Commit проверяет владельца binding, hash, тип person и avatarVersion, а неуспешная гонка очищает новый объект.
- Публичные режиссёры читаются из рабочих участий и заявок: подтверждённый Creator — ссылка с `type=film`, pending — подпись; raw не нужен для рендера. Набор экспортных полей не расширяется.

### Управление текущими jobs

- Администратор останавливает один queued/running запуск отзывом token/lease; worker проверяет владение до handler и раз в секунду, mutation guards сохраняются. Отмена не отключает расписание, не откатывает уже сохранённое и не отменяет отдельные дочерние запуски.
- Экспорт при отмене не остаётся в queued/running; блокировки для всех вариантов отмены идут job → export. Инициализация репутации и enqueue атомарны; предыдущий активный run блокирует новое начало. Отмена не меняет уже ready экспорт и enabled репутацию.
- Публичный для администратора прогресс — проекция известных counters, а не dump payload. Курсор ID и position отдельного этапа не считаются общим процентом. [Сценарии и пределы](P1_RELIABILITY.md#текущие-задачи-и-остановка).


### Централизованное заполнение изображений Creator

- Создание Creator и подтверждение/перенос binding ставят `media.creator-image-fill` в той же транзакции. Нет поиска идентичности по имени; отсутствие binding означает ожидание подтверждённого источника. Активные задачи дедуплицируются по Creator и отпечатку активных bindings; устаревший отпечаток не запускает загрузку.
- Автозаполнение и общий массовый перенос сохраняют любое установленное изображение. Пустота проверяется до загрузки и под Creator lock; при commit повторно проверяются полный набор bindings, тип, avatarVersion, snapshot hash/descriptor/link и lease. Ручное удаление само по себе не запускает повторное заполнение.
- Порядок источников фиксирован: person FantLab → TMDB person; organization TMDB company → IGDB company. Следующий источник пробуется только при подтверждённом отсутствии изображения; ошибка API не служит fallback. Неоднозначность идентичности требует ручного решения. RAWG/BGG пока не дают автоматических изображений Creator.
- Массовая задача `media.creator-images-backfill` использует тот же координатор, фильтры типа и роли, keyset по Creator ID, фиксированный throughId и существующий checkpoint/lease. Роль проверяется по рабочим участиям через EXISTS, без дублирования Creator по фильмографии. Применение изображения и успешный checkpoint атомарны; raw/link не применяют имена, даты и описания.


### Каталог и запуск задач

- Реестр исполнения не равен общему меню. Размещение `general/domain/migration/none` задаётся каталогом; общий action и action миграций проверяют своё размещение сервером. Неизвестные новые типы по умолчанию не получают ручную точку входа.
- Редактирование расписания сохраняет его payload; формы изменяют только явно переданные параметры. Исторические переносы показываются в «Миграциях», внутренние handlers — только в предметном pipeline. Пустой каталог миграций остаётся доступной страницей.
- Удалённый тип сохраняет только название и причину снятия для журнала. Его нельзя поставить заново или повторить; поздний старый run завершается терминальной ошибкой job-type-retired.
- Инициализация репутации получает initializationRequested только в атомарном предметном действии. Порядок постановки: enqueue advisory → active runs → settings; worker/cancel не берут enqueue advisory. Ошибка/отмена не меняет enabled; cleanup требует маркер владельца, текущий lease и initializing. Старый run с пустым payload не получает полномочия автоматически. Восстановление orphaned initializing запускается явно из настроек, только без активного расчёта.
- Явное обновление изображения Creator выбирает подтверждённый binding и разрешено только для пустого изображения или того же provider/external ID. Массовое заполнение по-прежнему сохраняет любое установленное изображение.

- После подтверждения администратором завершённости production-переносов их семь исторических handlers удалены. Вкладка миграций сохраняется пустой; retired metadata обслуживает только журнал и запрет повторов. Удаление игровых checkpoint-таблиц в 0139 защищено проверкой active jobs/незавершённых checkpoint-записей и не удаляет доменные сущности, источники или snapshots.
